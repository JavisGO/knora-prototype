# Knora 产品蓝图原型

入口页面是 `index.html`，用 Chrome 直接打开即可，不需要启动任何服务。

仓库地址：https://github.com/JavisGO/knora-prototype

有两种协作方式，选一种用就行：用 GitHub Desktop 点按钮操作（第一至五节），或者让 Claude Code / Codex 这类 Agent 代劳 git 操作（第六节）。两种方式遵守同样的规则。

---

## 一、首次准备（每人只做一次）

1. **注册并登录 GitHub**，把用户名发给仓库负责人，等待邀请邮件，点 **Accept invitation** 接受。
2. **安装 GitHub Desktop**：https://desktop.github.com ，打开后用 GitHub 账号登录。
3. **克隆仓库**：GitHub Desktop 菜单 **File → Clone repository**，在列表里选 `JavisGO/knora-prototype`，选好本地存放位置，点 **Clone**。

完成后，本地就有一份完整的原型，以后都在这个文件夹里改，**不要再复制文件夹**。

---

## 二、日常流程（每个需求走一遍）

### 1. 开工前先拉取最新版本

- 左上角 **Current branch** 切到 `main`。
- 点顶部 **Fetch origin**，如果有更新，按钮会变成 **Pull origin**，再点一下。

这样你是在别人最新的成果上开始改，后面合并时就不容易冲突。

### 2. 新建分支

- **Current branch → New branch**，输入分支名，点 **Create branch**。
- 分支名格式：`姓名缩写/需求`，例如 `xjw/kb-upload-config`。
- 一个需求一个分支，不要在一个分支里混着改好几件事。

### 3. 修改原型

- 照常用编辑器或 AI 工具修改本地文件夹里的页面。
- 改的过程中，GitHub Desktop 左侧 **Changes** 会实时列出改了哪些文件，点开就能看到具体改动（绿色是新增，红色是删除）。

### 4. 提交（Commit）

- 在左下角 **Summary** 写一句说明，写清楚改了哪个页面、改了什么，例如：`知识库上传：新增分片配置步骤`。
- 点 **Commit to 你的分支名**。
- 可以改一点提交一次，提交只存在自己电脑上，不影响别人。

### 5. 推送（Push）

- 点顶部 **Publish branch**（第一次推送）或 **Push origin**（之后再推送），把分支上传到 GitHub。

### 6. 提合并请求（Pull Request）

- 推送后点 **Create Pull Request**，浏览器会打开 GitHub 页面。
- **标题**：需求名称。
- **描述**：改了哪些页面、哪些入口，有没有改公共文件（`assets/` 下的共享样式和脚本）。
- 点 **Create pull request**。

### 7. 合并

- 在合并请求页面点 **Files changed**，最后确认一遍改动。
- 页面显示 **This branch has no conflicts with the base branch** 时，点 **Merge pull request → Confirm merge**。
- 合并后分支会自动删除。在群里说一声，其他人开工前拉取一下即可。

## 三、遇到冲突怎么办

**冲突**是指你和别人改了同一个文件的同一处，git 无法判断该保留谁的，需要人来选。只要分工清楚，这种情况很少出现。

处理步骤：

1. 在 GitHub Desktop 里切到你的分支，菜单 **Branch → Update from main**，把最新的 `main` 合进你的分支。
2. 如果有冲突，GitHub Desktop 会列出冲突文件。点 **Open in editor** 打开，冲突处会这样标出：

   ```
   <<<<<<< HEAD
   你的写法
   =======
   main 上别人的写法
   >>>>>>> main
   ```

3. 保留正确的那一份（也可以两份都保留并整理好），删掉 `<<<<<<<`、`=======`、`>>>>>>>` 这三行标记，保存。
4. 回到 GitHub Desktop，所有冲突文件处理完后点 **Continue merge**，再 **Push origin**。
5. 回到合并请求页面，冲突提示消失后就能正常合并了。

拿不准该保留哪一份时，先别合并，找改了另一边的同事一起确认。

## 四、协作规则

1. **`main` 受保护**：所有改动都必须通过合并请求合入，不能直接推送到 `main`。
2. **开工先拉取**：每次新建分支前，先切到 `main` 拉取最新版本。
3. **按页面分工**：每次迭代开始时说清楚谁改哪几个页面。公共文件（`assets/` 下的共享样式和脚本、侧边栏、首页导航）由一个人负责，其他人需要改时先打招呼。
4. **分支要小、要快**：一个需求一个分支，改完尽快合并。分支拖得越久，和 `main` 的差距越大，越容易冲突。
5. **CSS 保持多行**：一条样式规则占一行，不要压缩成一整行，否则 git 会把不相干的改动误判成冲突。让 AI 改原型时，也要提醒它不要压缩 CSS。
6. **临时文件不上传**：验证截图、浏览器缓存、临时文件放在 `_qa/`、`qa/`、`tmp/` 里，这些目录已设置为不上传。
7. **注意公开范围**：本仓库是公开仓库，任何人都能看到。不要放客户的真实数据、账号密码、合同等敏感内容。

## 五、常见问题

**改错了，想撤回还没提交的改动？**
在 **Changes** 里右键该文件，选 **Discard changes**。

**已经合并进 `main` 了，发现有问题？**
在 GitHub 上打开那个合并请求，点 **Revert**，会生成一个撤销用的新合并请求，合并它即可，历史记录都会保留。

**想找回某个旧版本？**
GitHub Desktop 的 **History** 里能看到每一次提交。标签 `baseline-v4` 是原型最初导入时的原样版本。

**不小心在 `main` 上改了文件？**
不要提交。直接 **New branch** 新建分支，GitHub Desktop 会问是否把改动带到新分支，选 **Bring my changes**，之后照常走流程。

## 六、用 Agent（Claude Code / Codex）协作修改

Agent 可以代替 GitHub Desktop，完成克隆、拉取、建分支、提交、推送和提合并请求，你只需要用自然语言说明要做什么。规则和前面一致，下面按"准备、第一次、日常、给 Agent 的规则"来写。

### 1. 准备（每人只做一次）

1. 安装 **git** 和 **GitHub CLI（gh）**：`brew install git gh`。
2. 登录 GitHub：运行 `gh auth login`，选 GitHub.com，协议选 **HTTPS**，按提示在浏览器里授权。Agent 提合并请求用的就是这个登录。
3. 安装并登录 **Claude Code** 或 **Codex**，按各自官方说明操作。
4. 接受仓库邀请（同第一节第 1 步）。

### 2. 第一次：让 Agent 克隆并了解仓库

在你想存放原型的文件夹里启动 Agent（Claude Code 运行 `claude`，Codex 运行 `codex`），然后说：

```text
把 https://github.com/JavisGO/knora-prototype 克隆到当前目录，进入后先完整阅读 README.md，
之后我们改原型都按里面的协作规则来。读完告诉我你理解的规则要点。
```

本仓库目前没有 `AGENTS.md`（Codex 自动读取）或 `CLAUDE.md`（Claude Code 自动读取），所以每次开新对话时，第一句话要让 Agent 先读 README，它才知道这里的规则。

### 3. 日常：每个需求这样对 Agent 说

**① 开工：同步并新建分支**

```text
切到 main 并拉取最新版本，然后新建分支 xjw/知识库上传配置。
```

分支名按 `姓名缩写/需求` 写。

**② 修改：描述需求，并带上约束**

```text
把 portal-resources.html 的上传文档弹窗增加"解析方式"选择，参考 knowledge-base-management.html 里的写法。
只改和这个需求相关的页面；CSS 保持一条规则一行，不要压缩；如果要改 assets/ 下的共享文件，先告诉我。
```

**③ 自查：改完先看效果**

```text
用浏览器打开改过的页面，检查有没有报错，再把改了哪些文件列给我。
```

**④ 提交、推送、提合并请求**

```text
先运行 git status 让我确认改动范围。确认后提交，说明写清楚改了哪个页面、改了什么，
然后推送分支，并用 gh 提一个合并请求，描述里写改了哪些页面、有没有改公共文件。
```

**⑤ 合并：由你确认**

合并请求提好后，Agent 会给出链接。你在 GitHub 页面看过改动，没问题再点 **Merge**，或者明确告诉 Agent"可以合并"。

**⑥ 合并后：同步**

```text
切回 main 并拉取最新版本，把已经合并的本地分支删掉。
```

**想接着改别人刚合并的内容时**，先让 Agent 拉取最新的 `main`，再从它新建分支，不要在旧分支上继续改。

### 4. 给 Agent 的规则（Agent 必须遵守）

以下规则同样适用于人工操作，写在这里是为了让 Agent 读到后直接照办：

1. **不在 `main` 上改**：所有改动都在自己的分支上做，不直接推送 `main`，不强制推送。`main` 已设置保护，只能通过合并请求合入。
2. **先拉取再建分支**：新建分支前，先切到 `main` 执行 `git pull`，保证从最新版本开始。
3. **分支名**：`姓名缩写/需求`，一个需求一个分支。
4. **只改需求相关的文件**：公共文件（`assets/` 下的共享样式和脚本、侧边栏、首页导航）改动前先告知用户，由用户确认。
5. **CSS 保持多行**：一条规则占一行，不要把样式压缩成一整行，也不要对无关的代码做整体重排，否则合并时会误判冲突。
6. **提交前检查范围**：先运行 `git status`，把改动文件列给用户确认。`_qa/`、`qa/`、`tmp/`、浏览器缓存和 `.DS_Store` 已被忽略，不要强行加入。
7. **提交说明写清楚**：写明改了哪个页面、改了什么，不写"更新""修改"这类笼统的话。
8. **冲突由用户决定**：遇到冲突时，先把两边的写法列给用户，等用户选择保留哪一份，不要自行覆盖任何一边。
9. **合并前先让用户确认**：提好合并请求后把链接交给用户，用户确认后才能合并。
10. **不放敏感内容**：仓库是公开的，不要提交客户真实数据、账号、密码和合同。

### 5. Claude Code 与 Codex 的区别

| | Claude Code | Codex |
|---|---|---|
| 启动 | 在仓库目录运行 `claude` | 在仓库目录运行 `codex` |
| 自动读取的项目说明文件 | `CLAUDE.md` | `AGENTS.md` |
| 本仓库现状 | 暂无该文件，需要第一句话让它读 README | 暂无该文件，同左 |

两者做 git 操作的方式相同，上面的话术都可以直接使用。

### 6. 常见问题

**克隆或推送提示连接被重置？**
网络波动，重试一次；仍然失败时，让 Agent 改用 HTTPS 地址 `https://github.com/JavisGO/knora-prototype.git`，不要用 `git@github.com:` 开头的 SSH 地址。

**Agent 说没有权限提合并请求？**
先运行 `gh auth status` 确认已登录，并确认已经接受了仓库邀请。

**Agent 不小心在 `main` 上改了文件？**
让它先别提交，新建分支并把改动带过去：`git switch -c 姓名缩写/需求`，之后照常提交推送。

**Agent 想把整个文件夹重新生成或覆盖？**
拒绝。只允许修改需求涉及的页面，整体覆盖会冲掉其他人的改动。
